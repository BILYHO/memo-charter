# 显式失败，不要静默成功

> **一句话口号**：最贵的 bug 是看起来成功的那种——别让失败藏起来。

## 规则

### 不要用"完成了"掩盖部分失败
- 跳过、丢弃、约束冲突的记录 → **必须显式上报数量与原因**，不能只写进日志深处
- 迁移/批处理报"成功"前，核对**处理数 vs 应处理数**，对不上就报警而非收尾
- 函数"能跑"不等于"返回对的值"——验证的是结果正确，不是没抛异常

### 失败要可见
- 错误向上冒泡或显式标注，不要静默吞掉(swallow)
- 真实案例：一次数据库迁移报"成功"，实则静默跳过了 14% 触发约束的记录，11 天后报表异常才被发现

### 兜底成功 ≠ 主路径健康

上面两节都假设「有一个失败事件，只是被吞了」。还有一种更隐蔽的形态：
**加了兜底之后，根本不再产生失败事件**——兜底每次都成功，于是
「主路径到底走没走通」这个问题被整个绕过，没有任何信号。

- 给一条路径加**兜底 / 预注入 / 缓存 / 默认值 / fallback 分支**时，
  兜底必须**报告主路径走没走通**（哪怕只是一行 "primary path unavailable, using fallback"）。
  不报告的兜底 = 把故障转成永久静默。
- 主路径里的**外部引用**（文件路径、URL、符号名）要能被机械校验。
  引用的东西删了、改名了，没人会来通知你；靠人眼复读一份配置是查不出来的。
- 判据一句话：**"如果主路径现在就断了，我会在多久之后、通过什么信号知道？"**
  答不上来，就是还差一个信号。
- 真实案例（2026-08-07）：`~/.claude/CLAUDE.md` 的「你必须先做的事」第 1 步指向
  `HANDOFF.en.md`，该文件在双语下线时已删除。因为 SessionStart hook 每次都成功注入
  distill 精华层，会话表现完全正常，**断链跨两个会话、一整天无人察觉**，
  直到为别的事去读那份配置才撞见。
  机制性根因：该文件被刻意排除在 `.setup-targets.yml` 的软链清单外
  （「手工维护的实体文件，不走 symlink」），因此它与仓库之间**没有任何自动一致性保障**——
  仓库删文件，它永远不会知道。

## 为什么

静默成功会把问题推迟到下游、放大排查成本。
显式失败让用户当场就能判断处理，符合本仓库 P1"暴露不确定/暴露权衡"的同一逻辑——只是延伸到了执行结果层面。

兜底那一节是同一逻辑再延伸一层：**兜底是为了让系统在故障时还能用，不是为了让故障看不见**。
二者可以兼得，代价只是一行日志；不兼得时，系统会带着一个坏掉的主路径正常运行到你需要它的那天。
